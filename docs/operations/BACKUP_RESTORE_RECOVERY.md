# Backup, Restore & Recovery

Operational runbook for the XDR platform's recoverable state.
Enforced by: `python scripts/xdr_recovery_validate.py`

---

## 1. State Inventory

The XDR platform's recoverable state lives in four places:

| Component | What is stored | Backup method |
|---|---|---|
| **PostgreSQL** | All SOC state: `security_alerts`, `security_incidents`, all append-only audit tables, tenant isolation tables, investigation graph, detection registry, pilot/governance history | `pg_dump` |
| **Configuration** | `.env` (secrets + service endpoints), `docker-compose.yml` (infra topology) | Secure secret store / version control (env example only) |
| **Rule Registry** | `docs/detection/rules/registry.v1.json` — 133 rules, promotion gates | Git |
| **Validation Reports** | `reports/*.json` — generated by validators, regeneratable | Rerun validators after restore |

**Not backed up** (ephemeral or recoverable without backup):
- Redpanda topic offsets — consumers auto-reset to `latest` on fresh deploy
- OpenSearch alert index — repopulated from PostgreSQL `security_alerts`
- Qdrant vector store — repopulated from RAG seeding runbook
- ClickHouse analytics rows — regenerated from event replay
- PHP application code — in Git
- Python/Go service code — in Git
- Laravel migrations — in Git; rerun `php artisan migrate` after restore

## 2. PostgreSQL Backup

### 2.1 Backup Command

```bash
# Full custom-format backup (recommended)
pg_dump -Fc \
  -h ${DB_HOST:-127.0.0.1} \
  -p ${DB_PORT:-5432} \
  -U ${DB_USERNAME:-postgres} \
  ${DB_DATABASE:-detector} \
  > detector_$(date +%Y%m%d_%H%M%S).dump

# Verify backup is readable
pg_restore --list detector_*.dump | head -20
```

### 2.2 Restore Command

```bash
# Create a fresh target database
createdb -h 127.0.0.1 -U postgres detector_restored

# Restore from dump
pg_restore -Fc \
  -h 127.0.0.1 \
  -U postgres \
  -d detector_restored \
  detector_YYYYMMDD_HHmmss.dump

# Verify row counts in critical tables
psql -h 127.0.0.1 -U postgres -d detector_restored \
  -c "SELECT count(*) FROM security_alerts; SELECT count(*) FROM security_incidents;"
```

**Safety rules:**
- NEVER restore directly to the production database without verifying the dump first on a separate host.
- Always validate with `php artisan migrate:status` after restore to confirm no pending migrations.
- Append-only tables (`export_audit_logs`, `investigation_events`, etc.) must never be truncated.

### 2.3 Append-Only Table Guard

The following tables must never have rows deleted or updated (only INSERT allowed).
Verify after restore that row counts match the pre-backup snapshot:

```sql
SELECT 'export_audit_logs', count(*) FROM export_audit_logs
UNION ALL SELECT 'investigation_events', count(*) FROM investigation_events
UNION ALL SELECT 'advisory_finding_events', count(*) FROM advisory_finding_events
UNION ALL SELECT 'dlq_normalization_events', count(*) FROM dlq_normalization_events
UNION ALL SELECT 'tenant_boundary_violation_reports', count(*) FROM tenant_boundary_violation_reports;
```

## 3. Configuration Backup

### 3.1 What to Back Up

| File | Contents | Backup method |
|---|---|---|
| `.env` | All secrets, DB DSN, service URLs | Secure secret store (e.g., HashiCorp Vault, AWS Secrets Manager). **Never commit .env to Git.** |
| `.env.example` | Template with all keys and safe placeholder values | Git — committed |
| `docker-compose.yml` | Infrastructure topology: ports, volumes, profiles | Git — committed |
| `docker-compose.override.yml` | Local overrides (if present) | Developer-local; document but do not commit |

### 3.2 Required Keys for Recovery

All keys in `.env.example` must be present in `.env` before the platform can start.
Critical keys that must have non-placeholder values for staging/production:

```env
APP_KEY=          # 32-byte base64 key; generate: php artisan key:generate --show
DB_HOST=          # PostgreSQL host
DB_PORT=          # PostgreSQL port
DB_DATABASE=      # PostgreSQL database name
DB_USERNAME=      # PostgreSQL username
DB_PASSWORD=      # PostgreSQL password
XDR_INGEST_SECRET=            # HMAC secret for ingestion-gateway
XDR_INTERNAL_AUTH_SECRET=     # Internal service auth bearer token
```

Generate secrets:
```bash
openssl rand -hex 32   # for XDR_* secrets
php artisan key:generate --show  # for APP_KEY
```

## 4. Validation Reports

Reports under `reports/` are generated outputs — they are NOT source of truth.
They document what was validated at a point in time and can be regenerated.

**Key reports and how to regenerate them:**

| Report | Regeneration command |
|---|---|
| `reports/xdr_contract_validation.json` | `python scripts/xdr_contract_validate.py --output reports/xdr_contract_validation.json` |
| `reports/xdr_rule_registry_validation.json` | `python scripts/xdr_rule_registry_validate.py` |
| `reports/xdr_fleet_simulation_validation.json` | `python scripts/xdr_fleet_simulation_validate.py` |
| `reports/xdr_correlation_soak_6h.json` | `powershell -File scripts/run_xdr_correlation_soak_6h.ps1` |
| `reports/xdr_ingestion_hardening_validation.json` | `python scripts/xdr_ingestion_hardening_validate.py --output reports/xdr_ingestion_hardening_validation.json` |
| `reports/posture_check.json` | `python scripts/xdr_posture_check.py --profile=local --output reports/posture_check.json` |

After a restore, regenerate the rule registry report first:
```powershell
python scripts/xdr_rule_registry_validate.py
```
Expected: `status=PASS rules=133 checks=21/21`

## 5. RPO / RTO Targets

| Profile | RPO | RTO | PostgreSQL backup | Notes |
|---|---|---|---|---|
| **local** | N/A (dev only) | < 5 minutes | Not required | `php artisan migrate:fresh --force` resets state |
| **staging** | 24 hours | < 60 minutes | Daily `pg_dump` | Restore to staging only; never overwrite production |
| **production-pilot** | 4 hours | < 30 minutes | Every 4h `pg_dump` or WAL-based PITR | Test restore to a separate host before every production cutover |

**Definition of RTO start:** time from recognizing a data-loss event to the platform accepting new alerts with full SOC state restored.

**Definition of RPO:** maximum acceptable data age at restore time. A 4h RPO means we tolerate losing up to 4 hours of alerts/incidents in the worst case.

## 6. Recovery Procedure

### 6.1 Full Recovery (production-pilot)

1. **Declare incident** — note the time of last known-good backup.
2. **Stop pipeline services:**
   ```bash
   docker compose --profile strangler stop
   ```
3. **Restore PostgreSQL:**
   ```bash
   pg_restore -Fc -h $DB_HOST -U $DB_USERNAME -d $DB_DATABASE \
     detector_YYYYMMDD_HHmmss.dump
   ```
4. **Run migrations** (idempotent — safe to rerun):
   ```bash
   php artisan migrate --force
   ```
5. **Verify schema integrity:**
   ```bash
   php artisan migrate:status
   ```
6. **Restart services:**
   ```bash
   docker compose up -d
   docker compose --profile strangler up -d
   ```
7. **Run post-recovery validation** (section 7 below).
8. **Resume alert ingestion** only after validation passes.

### 6.2 Configuration-Only Recovery

If `.env` is lost but the database is intact:
1. Start from `.env.example` as the template.
2. Re-inject all secrets from the secure secret store.
3. Run `php artisan config:clear && php artisan cache:clear`.
4. Verify with `python scripts/xdr_posture_check.py --profile=staging`.

## 7. Post-Recovery Validation

Run these commands in order after any restore. All must pass before declaring recovery complete.

```powershell
# 1. Schema
php artisan migrate:status

# 2. Application tests (targeted — schema + core model integrity)
php artisan test --filter=SecurityAlertsTest
php artisan test --filter=TenantIsolationTest

# 3. Rule registry
python scripts/xdr_rule_registry_validate.py
# Expected: status=PASS rules=133 checks=21/21

# 4. Recovery readiness
python scripts/xdr_recovery_validate.py --profile=staging
# Expected: overall=PASS

# 5. Posture check
python scripts/xdr_posture_check.py --profile=staging
# Expected: overall=PASS or WARN (no FAIL)

# 6. Contract validation (requires --profile strangler stack)
python scripts/xdr_contract_validate.py --output reports/xdr_contract_validation.json
```

**STOP condition:** If any step above fails, do not resume production ingestion.
Investigate root cause before proceeding.

## 8. What the Recovery Validator Checks

`python scripts/xdr_recovery_validate.py` is a read-only, non-destructive readiness checker.
It verifies that backup preconditions are in place without touching the database.

| Check ID | What it validates |
|---|---|
| R-01 | PostgreSQL DSN keys present in `.env` |
| R-02 | `.env.example` present as recovery template |
| R-03 | `docker-compose.yml` present (infrastructure config) |
| R-04 | Rule registry is parseable and has expected rule counts |
| R-05 | Database migrations directory has expected file count |
| R-06 | At least one key validation report exists under `reports/` |
| R-07 | Required operational documentation is present |
| R-08 | This backup/restore runbook itself is present |

```powershell
# Dry-run (no filesystem side effects)
python scripts/xdr_recovery_validate.py --dry-run

# With profile and JSON report
python scripts/xdr_recovery_validate.py --profile=staging \
  --output reports/recovery_validation.json
```

Exit codes: `0` = PASS, `1` = FAIL, `2` = ERROR
